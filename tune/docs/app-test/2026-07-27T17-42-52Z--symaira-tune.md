## Verdict

The app launches cleanly from HEAD, registers its menu-bar status item, and correctly shows no
update badge (HEAD 0.3.1 is ahead of the latest release v0.3.0). No crash reports were produced.

The most important finding is that the popover's **Software Dimming slider is inverted and cannot
return the screen to undimmed**: the core treats the dim value as a brightness multiplier where
`1.0` means "no dim", while the app's slider spans `0.0...0.85` and labels it as an amount of
dimming. The app's "0%" position is applied as an 85% black overlay, and the value that means
"no dim" lies outside the slider's range entirely. This is confirmed by the app's own history log,
not inferred: `dim.set 0.00 0.15 0.15 success`.

Secondary risk sits in the fan surface, which presents itself as functional on a machine that
reports no fans, and reports success for a restore that provably did nothing.

The areas carrying unquantified risk are the ones that could only be reached through the popover:
popover placement and clipping (the subject of an explicit code comment in
`Sources/SymTuneApp/StatusBarController.swift:66`), the 3-second refresh loop's effect on
in-progress slider drags, keyboard navigation, and whether Quit restores every override.

## Findings

- [ ] **[App/BROKEN] Software Dimming slider is inverted and cannot restore an undimmed screen**
  - **Status quo:** `DimOverlay.applyDimOnMain` computes `overlayAlpha = CGFloat(1.0 - opacity)` (`Sources/SymTuneCore/DimOverlay.swift:39`), so the core's scale is a brightness multiplier: `1.0` = no dim, `0.15` = darkest. `currentOpacity` is initialised to `1.0`, and the CLI documents the matching range `dim set <0.15-1.0>`. The app instead declares `Slider(value: $dim, in: 0.0...0.85)` with the label "Software Dimming" and a readout of `Int(dim * 100)%` as an *amount* of dimming, passing the raw value to `controller.applyDim` (`Sources/SymTuneApp/MainStatusView.swift:81`). Three consequences follow: the slider's `0.0` floor, labelled "0%", is clamped to `SafetyPolicy.dimMin` = `0.15` and applied as an 85% black overlay — recorded verbatim in the app's history log as `dim.set 0.00 0.15 0.15 success`; the slider's maximum `0.85`, labelled "85%", is in fact a 15% dim; and `1.0`, the only value meaning "no dim", is outside the slider's range, so once the slider is touched the app can no longer restore an undimmed screen (recovery requires Quit or `symtune dim reset`). Additionally `refreshData()` assigns `dim = controller.getDimLevel()` = `1.0` on open (`Sources/SymTuneApp/MainStatusView.swift:324`), which is out of the slider's range, so a freshly opened popover reads "Software Dimming 100%" on an undimmed screen.
  - **Repro:** 1. Launch SymairaTune and click the menu-bar slider icon. 2. Observe the Software Dimming row on first open. → It reads "100%" although the screen is not dimmed. Expected: "0%" on an undimmed screen. 3. Drag the Software Dimming slider fully to the left, to its "0%" position. → The screen darkens dramatically (85% black overlay). Expected: "0%" means no dimming. 4. Drag the slider fully to the right, to "85%". → The screen becomes only slightly dimmed. Expected: "85%" is darker than "0%", not lighter. 5. Try to return the screen to fully undimmed using only this slider. → Impossible; no slider position corresponds to no dim. Expected: the slider can restore an undimmed screen.
  - **Proposed solution:** Pick one direction and make the whole surface agree. The lower-risk fix is to keep the core's multiplier semantics and convert at the view boundary: drive the slider over `0.0...0.85` as a dim *amount* but pass `1.0 - dim` into `applyDim`, and map `getDimLevel()` back with `1.0 - level` when reading state in `refreshData()`. That keeps "0% = no dim" true, makes the maximum the darkest setting, and lets the slider reach genuine zero dim. Add a regression test asserting that the view's `0%` maps to an applied core value of `1.0` and that the maximum maps to `dimMin`.
  - **Effort/Impact:** Low effort / high impact — a two-line conversion at the view boundary fixes a primary control that currently does the opposite of what it says and strands the user on a dimmed screen.

- [ ] **[App/BUG] Returning fans to automatic control reports success on hardware with no fans**
  - **Status quo:** `FanControlService.restoreAuto()` reads `FNum`, and on `fanCount == 0` returns early with no error and no signal (`Sources/SymTuneCore/FanControlService.swift:158`). On this fanless host `symtune fan auto` therefore prints `{"applied": true}` and exits `0`, while the sibling write path `applyFan` correctly throws `FanControlError.noFansDetected` and surfaces `unsupported: SMC reports no fans; fan control is unavailable` with exit `4`. The history log records the same asymmetry from one session: `fan.set 0.50 0.50 n/a failed no fans detected` immediately followed by `fan.auto n/a n/a n/a success`. The app's Fan Control toggle drives this same method on its off path (`Sources/SymTuneApp/MainStatusView.swift:360`), so switching the toggle off clears `fanError` and reports success without anything having been restored. `applied: true` is the tool's machine-readable answer to an agent, which makes a false success here more costly than a cosmetic one.
  - **Repro:** 1. On a Mac that reports no fans (`symtune sensors` shows `"fans": []` and the note "No fans detected"), run `symtune fan set 0.5`. → Correctly reports `unsupported: SMC reports no fans; fan control is unavailable`, exit 4. 2. Run `symtune fan auto`. → Reports `{"applied": true}`, exit 0. Expected: the same unsupported/no-fans signal as step 1, since no fan was or could be restored.
  - **Proposed solution:** Make `restoreAuto()` distinguish "restored" from "nothing to restore". Have it throw `FanControlError.noFansDetected` on `fanCount == 0` for parity with `applyFan`, or return a result the callers can report honestly so `fan auto` emits an unsupported status rather than `applied: true`. Keep the app's toggle-off path from clearing its error state when nothing was actually restored.
  - **Effort/Impact:** Low effort / medium impact — small change, but it removes a false success from the surface agents consume.

- [ ] **[App/UX] Fan Control card is presented as functional on hardware that has no fans**
  - **Status quo:** The popover renders the Fan Control card unconditionally, with an enabled toggle and a Target Speed slider, and no unsupported state (`Sources/SymTuneApp/MainStatusView.swift:131`). The Extended Brightness control directly above it is properly capability-gated behind `isEDRCapable` (`Sources/SymTuneApp/MainStatusView.swift:105`), so the pattern for hiding an unavailable capability already exists in the same view. On this host the capability is genuinely absent — `symtune sensors` reports `"fans": []` with the note "No fans detected (fanless Mac or SMC returned fan count 0)". The user can therefore enable a control that cannot work; the failure only becomes visible after they flip the toggle, as a small red error string. This contradicts the requirement recorded in `docs/manual-app-verification.md`, that on machines without the required hardware "the UI must report unavailable or unsupported capabilities rather than presenting them as working".
  - **Repro:** 1. On a Mac that reports no fans (`symtune sensors` shows `"fans": []`), launch SymairaTune and open the popover. 2. Look at the Fan Control card. → The toggle is enabled and presented as usable, with no indication fan control is unavailable on this machine. Expected: the card is hidden, or shown with an explicit unsupported state and a disabled toggle, matching how Extended Brightness is gated. 3. Flip the toggle on. → It springs back and a red error appears. Expected: the unavailability is communicated before the user interacts.
  - **Proposed solution:** Gate the Fan Control card on detected fan availability the same way Extended Brightness is gated on `isEDRCapable` — derive a `hasFans` flag from the sensor report already fetched in `refreshData()` and either omit the card or render it disabled with a short "not available on this Mac" line. Prefer showing a disabled, explained card over hiding it entirely, so the absence reads as a hardware fact rather than a missing feature.
  - **Effort/Impact:** Low effort / medium impact — mirrors an existing pattern in the same file and stops the UI offering a control the hardware cannot honor.

## Considered and dropped

- `swift build` fails on the `SymTuneApp` target — the same command succeeds with `DEVELOPER_DIR` pointing at the installed Xcode. The host's `xcode-select` points at CommandLineTools, which cannot build the SwiftUI target. Environment, not defect.
- `symtune brightness set 5.0` returns `{"applied": true}` without reporting that the value was clamped to `1.0` (history: `brightness.set 2.00 1.00 1.00 success`). Real but out of scope for the app surface, and the clamp itself is correct and intentional; worth a separate look at whether the CLI/MCP responses should echo the applied value.
- CLI exit codes were checked and are correct (`4` for unsupported, `2` for an unknown command); an earlier apparent `0` was an artifact of reading `$?` through a pipe.
- No update badge on the status icon — correct behavior, since HEAD 0.3.1 is ahead of the latest release v0.3.0.
- No crash reports for the app in `~/Library/Logs/DiagnosticReports/`.

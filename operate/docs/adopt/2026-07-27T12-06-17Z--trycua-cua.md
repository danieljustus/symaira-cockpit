## Verdict

`trycua/cua` is a genuinely high-value SOURCE for this repo: `libs/cua-driver` solves
the same problem as `symoperate` — drive native macOS apps for an agent, over MCP,
with an accessibility tree and safety refusals — and it has been beaten on by far more
real-world hosts. Most of the repo does not transfer (background/no-foreground input,
VM fleets, benchmark harnesses, a Rego permission engine, UniFFI SDK generation), and
the TARGET's own safety model is *stronger* than theirs for a supervised local tool.

The value is concentrated in one theme: **cua treats the agent-facing wire as a typed
contract, and the TARGET treats it as prose.** Refusals carry stable machine-readable
codes instead of English sentences, the stdio framing follows the MCP spec rather than
LSP, permission status names *which* TCC identity it describes, and an action counts as
"delivered" only when an effect was observed. Four findings, all in that theme, all
reversible.

The single highest-value takeaway: safety refusals should be successful tool results
carrying a stable `code`, not JSON-RPC `-32000` errors with free text.

## What we already do as well or better

  `snapshot_id` + `element_id` with a bounded FIFO cache and a dedicated
  `AutomationError.staleReference` (`Sources/SymOperateCore/AccessibilityService.swift:83`);
  equivalent to their per-`(pid, window_id)` `element_index` + turn model.
- OCR fallback when the AX tree is too thin → `Sources/SymOperateCore/OCRService.swift`
  plus `queryUIWithOCR` and the `axTreeWeak` flag
  (`Sources/SymOperateCore/AutomationController.swift:80`); cua surfaces the same
  condition as an inline warning in `get_window_state`. Comparable.
- Built-in destructive-control refusal and secure-field blocking →
  `Sources/SymOperateCore/ActionPolicy.swift:22` and
  `Sources/SymOperateCore/AutomationController.swift:292`. **We are ahead here.**
  cua-driver ships no equivalent keyword guard; it defers to a separate YAML/Rego
  permission engine and consent modes, which is the wrong shape for a supervised local
  CLI.
- Audit log that never persists typed text → `Sources/SymOperateCore/HistoryService.swift`
  with redaction at `Sources/SymOperateCore/AutomationController.swift:180`. cua reaches
  the same guarantee through a much larger content-free telemetry observer
  (`libs/cua-driver/rust/crates/cua-driver-core/src/server.rs:260`). Ours is simpler for
  the same property.
- MCP as the language-neutral agent boundary instead of generated per-language SDKs →
  exactly what `Sources/SymOperateMCP/` already is. Their own
  `libs/cua-driver/docs/why-cua-driver-uses-mcp-instead-of-uniffi.md` argues the TARGET's
  existing position.
- Least-privilege workflow permissions and superseded-run cancellation →
  `.github/workflows/ci.yml:8` (`concurrency` + `cancel-in-progress`) and
  `.github/workflows/ci.yml:12` (`permissions: contents: read`). Already done, recently
  (#58).
- Floating GitHub Action tags: neither repo pins action SHAs (0 of 124 `uses:` in the
  SOURCE are SHA-pinned). No delta — this is not something to learn from them.

## Findings

- [ ] **[UX/DX] Return safety refusals as successful tool results with a stable code, not JSON-RPC errors**
  - **Status quo:** Every safety refusal in `Sources/SymOperateCore/AutomationController.swift:292,300,304,318,321` throws `AutomationError.permissionDenied` carrying only an English sentence, and `Sources/SymOperateMCP/MCPServer.swift:34` collapses *every* thrown error — refusal, expired snapshot, invalid argument, internal failure — into one JSON-RPC `-32000` with `error.message` set to that prose. The six-case classification in `AutomationError` (`Sources/SymOperateCore/Models.swift:255`) is already computed and then discarded at the MCP boundary; it survives only on the CLI path via `ExitCode`. An agent therefore cannot distinguish "the guard deliberately declined this element" from "your snapshot expired" from "the tool broke" without string-matching English, and a `-32000` reads to most MCP hosts as a tool failure whose natural recovery is retry — which will fail identically forever. Upstream solves this in `libs/cua-driver/rust/crates/cua-driver-core/src/browser/refusal.rs:1-125`: a closed, additive-only snake_case code vocabulary serialized as `{"status":"refused","refusal":{code,message,detail}}` into `structuredContent`, with the rationale stated in the module doc — *"NOT an MCP protocol error: the call executed correctly and its outcome is the refusal, so `isError` stays unset and agents branch on `structuredContent.status`."* The same discipline drives their whole "exact-or-refused" contract in `libs/cua-driver/docs/action-support.md:5-9`.
  - **Proposed solution:** Pattern adoption (no code copied; SOURCE is MIT so a copy would be permitted, but this is a 60-line Swift design). Add a stable `code: String` to `AutomationError` — a closed enum such as `destructive_control_refused`, `secure_field_refused`, `element_not_resolvable`, `stale_snapshot`, `invalid_argument`, `permission_not_granted` — and split the MCP boundary in `Sources/SymOperateMCP/MCPServer.swift` in two: deliberate refusals become a normal `tools/call` result with `isError: false` and `structuredContent: {status:"refused", refusal:{code, message}}`; genuine faults keep the JSON-RPC error path but gain the same `code` in `error.data`. Keep the existing human messages verbatim as the `message` field so nothing regresses for humans. Document the vocabulary in `SAFETY_AUDIT.md` alongside the existing guard list, and treat renames as breaking.
  - **Effort/Impact:** Medium effort / high impact. No new dependencies; additive and reversible (the error path can stay in place during migration, and the codes are useful on their own even if the `status:"refused"` shape is deferred). Directly improves the agent behavior the README's "Recommended agent loop" section depends on.

- [ ] **[UX/DX] Use newline-delimited JSON for the stdio MCP transport instead of LSP `Content-Length` framing**
  - **Status quo:** `Sources/SymOperateMCP/MCPServer.swift:394` writes `Content-Length: <n>\r\n\r\n` before every frame on stdout, and `Sources/SymOperateMCP/MCPServer.swift:401-431` requires that header on stdin, throwing `"Missing Content-Length header."` when it is absent — there is no newline-delimited fallback in either direction. That is Language Server Protocol framing; the MCP stdio transport is newline-delimited JSON-RPC (one message per line, no embedded newlines). Upstream's stdio MCP paths read line-by-line — `libs/cua-driver/rust/crates/cua-driver/src/proxy.rs:55` and `libs/cua-driver/rust/crates/cua-driver/src/private_worker.rs:74` (`stdin.lock().lines()`) — and `Content-Length` appears in their tree only inside `libs/cua-driver/rust/crates/cua-driver/src/mcp_http.rs`, where it is an HTTP header, not MCP framing. This is currently unverifiable from our own test suite: every MCP test calls `dispatch(method:params:)` directly (`Tests/SymOperateCoreTests/MCPServerTests.swift:13-192`), so `run()`, `readMessage` and `send` — the entire transport — have zero coverage, and `Tests/SymOperateSmokeTests/` never starts `serve`.
  - **Proposed solution:** Pattern adoption. Make `readMessage` accept both framings (peek for `Content-Length:` and otherwise treat the input as one JSON object per line) and switch `send` to emit a single compact JSON line terminated by `\n`. Accepting both on read keeps any currently-working host working; emitting newline-delimited on write is what makes spec-compliant hosts work. Add the missing loopback test: drive `MCPServer.run()` over a `Pipe`, write an `initialize` + `tools/list` exchange, and assert the response parses — that test is the real deliverable here, since it is what would have caught this.
  - **Effort/Impact:** Low effort / high impact — roughly 40 lines in one file plus one test, fully reversible. Removes a class of defect (silent handshake failure against any host that does not speak LSP framing) in the one code path that gates every other feature. See Open questions: whether this breaks against a specific host today is unconfirmed.

- [ ] **[Security] Report which TCC identity the permission booleans describe**
  - **Status quo:** `Sources/SymOperateCore/PermissionService.swift:8-13` answers with bare `AXIsProcessTrusted()` / `CGPreflightScreenCaptureAccess()`, and `Sources/symoperate/main.swift:113-140` reports those as `doctor`'s `permissions` block and `capabilities`. macOS attributes Accessibility and Screen Recording to the *responsible process* — the launching app — not to the executable path. So `symoperate doctor` run from Terminal reports **Terminal's** grants, and the README's install flow (`symoperate permissions grant accessibility`, then `symoperate doctor`) can report a fully green environment while the binary spawned by Claude Desktop is denied, because the grant landed on the wrong identity. `AGENTS.md:62` already hints at this ("the host process must be authorized") but nothing in the code or the user-facing output can distinguish the two cases, and nothing in `README.md`, `docs/architecture.md` or `SAFETY_AUDIT.md` explains it. Upstream treats this as a first-class part of the permission answer in `libs/cua-driver/rust/crates/platform-macos/src/tools/check_permissions.rs:80-170`: `check_permissions` returns a `source` object with an `attribution` field (`driver-daemon` / `host` / `caller`), the pid, responsible ppid, resolved executable path, and a plain-language note — the `caller` note reads *"These booleans reflect the TCC identity of the app that launched this process (e.g. your terminal/IDE), NOT an installed CuaDriver app bundle. A standalone check can read `true` here while the driver's bundle has no grant."* Their agent skill turns it into an operational rule (`libs/cua-driver/rust/Skills/cua-driver/MACOS.md:228-232`, detecting "a wrong-TCC context (any IDE-spawned shell: Claude Code, Cursor, VS Code, Conductor)").
  - **Proposed solution:** Pattern adoption. Extend `PermissionSnapshot` with a `source` block — pid, parent pid, resolved executable path, the responsible/launching process name where obtainable — and a short note stating that the booleans describe the launching app's grants. Surface it in `doctor` and in the `permissions_status` MCP tool, and add a `recommendations` line when `doctor` detects it was launched from a terminal or IDE rather than by the MCP host. Adopt the *reporting* half only; explicitly do **not** adopt their `.app`-bundle-with-daemon architecture (see rejected list). Then correct the README install sequence and add a short section to `SAFETY_AUDIT.md` under "Permission Boundaries".
  - **Effort/Impact:** Low-to-medium effort / high impact. No new dependencies, purely additive to an existing JSON shape, reversible. Turns the most likely "I granted it and it still says denied" support case into self-service, and makes `doctor` honest about what it actually measured.

- [ ] **[Architecture] Verify actions by observing an effect, not by the absence of a throw**
  - **Status quo:** `Sources/SymOperateCore/AutomationController.swift:140-150` builds every `ActionResult` with `ok: true` whenever the closure did not throw, and reports messages like `"Click delivered at (x, y)."` (`Sources/SymOperateCore/AutomationController.swift:167`) — but `CGEvent.post` has no read-back, so nothing observed a delivery. `ok` is a constant carrying no information, and `HistoryService` records `success: true` on the same basis. The tests mirror this: `Tests/SymOperateSmokeTests/SmokeTests.swift:47,62,77` are `testClickDoesNotCrash`, `testTypeTextDoesNotCrash`, `testPressKeysDoesNotCrash` — they assert that input synthesis does not throw, never that anything happened. The safety guards are well covered (`Tests/SymOperateCoreTests/SafetyPolicyTests.swift`, 724 lines), but the delivery path — the actual product — has no effect-level test at all. Upstream's rule is the inverse (`libs/cua-driver/docs/action-support.md:5-9`, 88-93): *"Delivered means a fixture-owned state change was observed"*, and *"When an OS API reports success but offers no effect read-back, retain a visible gap rather than inventing a fixture-specific refusal in production code."* They implement it with small single-file Swift fixture apps that render their own state into accessible labels the test reads back — `libs/cua-driver/tests/fixtures/apps/macos/appkit/main.swift:359` sets `checkStateLabel.stringValue = "agreed=\(sender.state == .on)"` so a test can confirm a click landed through the same AX tree the driver uses.
  - **Proposed solution:** Partial transfer, pattern adoption. Two separable pieces. (a) Cheap and immediate: stop asserting unobserved outcomes — reword `"Click delivered at …"` to state what was actually done (the event was posted) and reserve `ok: true` for outcomes with a read-back, so the agent's re-snapshot step is understood as required rather than optional. (b) Larger: add a ~200-line single-file AppKit fixture under `Tests/` that mirrors its control state into `setAccessibilityIdentifier`-tagged labels, plus a `make test-e2e` target that launches it, drives it by `element_id`, and asserts the fixture's own state changed. **This cannot run on GitHub-hosted `macos-15` runners** — they have no Accessibility or Screen Recording grants — so it must be a local, opt-in target, not a CI gate. Their CI runs the equivalent on logged-in self-hosted machines, which is out of scope here.
  - **Effort/Impact:** Part (a) low effort / medium impact; part (b) high effort / high impact. Reversible in both halves. Rank part (a) first — it is a wording and semantics fix worth doing regardless of whether (b) is ever built, and (b) should only be started if a delivery bug actually bites.

## Considered and rejected

- **Background / no-foreground computer use (drive apps without stealing focus)** — gate 1 (Transferable): their flagship capability rests on per-pid SkyLight event routing, a code-signed `CuaDriver.app`, and a persistent daemon. `symoperate` is a stdio-only CLI using public `CGEvent` APIs (`Sources/SymOperateCore/InputService.swift`) with no daemon by design (`SAFETY_AUDIT.md`, "Supervised, Local Operation"). Adopting it would invert the product's stated safety posture.
- **`CuaDriver.app` bundle + LaunchServices-routed daemon for stable TCC identity** — gate 4 (Worth it): it is the correct fix for the attribution problem, but it means shipping an app bundle, a daemon lifecycle, a re-exec-with-responsibility-disclaim path, and an embedded-host contract. Enormous surface for a one-binary Homebrew tool. The reporting half is adopted instead (see the Security finding).
- **Permission modes (`standard` / `bounded` / `unrestricted`) over a YAML/Rego policy engine** — gate 4 (Worth it) / scale fit: `libs/cua-driver/docs/driver-permission-modes-and-consent-plan.md` describes a driver-wide authorization model with protected approval collectors and revocable grants. Our entire policy is a keyword deny-list in `Sources/SymOperateCore/ActionPolicy.swift` (56 lines) that deliberately cannot be weakened. A Rego engine for that is orders of magnitude of cost for no added guarantee at this size.
- **Agent cursor overlay with dotLottie themes and motion tuning** — gate 4 (Worth it): demo and screen-recording polish requiring an overlay window and a UI event loop. Zero automation value, permanent maintenance surface.
- **Session recording + `replay_trajectory`** — gate 2 (New) / gate 4: we already keep an auditable action trail (`Sources/SymOperateCore/HistoryService.swift`, `symoperate history --json`). Full trajectory capture and replay serves their training/eval business, not a supervised local tool.
- **UniFFI-generated Python/TypeScript SDKs over a versioned C ABI** — gate 1 (Transferable): `symoperate` is Swift-only and MCP already *is* the language-neutral boundary. Their own `libs/cua-driver/docs/why-cua-driver-uses-mcp-instead-of-uniffi.md` reaches the conclusion we already implement.
- **Monorepo release tooling (`release-please`, 92 workflows, per-package `cd-*.yml`)** — gate 4 (Worth it) / scale fit: pays off across ~20 published packages in 8 languages. We have one binary and one `release.yml`.
- **`--claude-code-computer-use-compat` screenshot mode** — gate 3 (Better): it exists because their default `screenshot` is window-scoped and Claude Code needs a full-frame grounding anchor. Our `snapshot` already defaults to the full main display with transform metadata (`Sources/SymOperateCore/ScreenService.swift`), so there is nothing to compensate for.
- **`zoom` tool (native-resolution region capture with automatic coordinate mapping back)** — gate 3 (Better): plausible against our fixed 1280px downscale (`Sources/SymOperateCore/ServiceProtocols.swift:20`), but we have no recorded case where OCR or element resolution actually failed because of that downscale, and our element-first path reads text from the AX tree rather than pixels. Revisit if a real "the agent could not read the label" case appears.
- **Per-platform agent skill pack with progressive disclosure (`SKILL.md` + `MACOS.md`/`WINDOWS.md`/`LINUX.md`)** — gate 3 (Better): the structure exists to keep three OS documents out of each other's way. We are macOS-only and already split guidance across `AGENTS.md` (63 lines) and `docs/macos-agent-guide.md` (109 lines). Splitting further has no reader.
- **Structured browser refusals and CDP tab binding (`BROWSER.md`, `browser_*` tools)** — gate 1 (Transferable): we expose no browser surface. The refusal *mechanism* is adopted; the browser vocabulary is not.
- **`.editorconfig`, Prettier, `.pre-commit-config.yaml`** — gate 4 (Worth it): multi-language monorepo hygiene. We are single-language Swift with SwiftLint already gating CI (`.github/workflows/ci.yml:21`); adding a Python-based pre-commit runner to format 14 markdown files is net cost.
- **`cua-driver mcp-config --client claude` (prints the host registration snippet)** — gate 3 (Better): `README.md` already ships the exact JSON. The only delta is auto-filling the absolute path, which `brew install` already makes predictable.
- **`cua-driver list-tools` / `describe <tool>` CLI introspection** — gate 3 (Better): real but marginal. `tools/list` already returns the full schema set over MCP and `Tests/SymOperateCoreTests/MCPServerTests.swift:25` asserts it; a second CLI-side rendering of the same data buys convenience, not capability. Bundle it into the refusal-codes work if that touches the CLI anyway.
- **SHA-pinned GitHub Actions** — not a SOURCE idea: 0 of 124 `uses:` entries in their workflows are SHA-pinned, same as ours. Listed only so it is clear this was checked and is not something they do better.

## Open questions

- **Does the `Content-Length` framing actually fail against a real host today?** The README claims working Claude Desktop / OpenCode / Cursor integration, and some hosts tolerate both framings. The evidence here is one-directional (spec + a widely-deployed reference implementation), not an observed failure. Settled by: register `symoperate serve` with a stock MCP host and capture the raw stdio exchange, or run the loopback test proposed in that finding against a stock MCP client library.
- **How often does the TCC attribution problem bite in practice?** With Homebrew distribution the binary lives at a stable path, and some hosts may inherit a usable grant. Settled by: granting Accessibility to Terminal only, then launching `symoperate serve` from Claude Desktop and reading `permissions_status`. If it reports `true` there, the finding is documentation-only rather than a diagnostic gap.
- **Is the `axTreeWeak` threshold of 3 nodes (`Sources/SymOperateCore/ServiceProtocols.swift:88`) right?** Upstream warns at 11 elements for Blender. Neither repo publishes data behind its number. Settled by: sampling node counts across a handful of AX-poor apps (Blender, Electron apps, games) and picking the threshold from the distribution.
- **Motivation for the refusal-code design could not be traced to a commit** — the shallow clone flattens history, so `git log` on `refusal.rs` shows only `e9852cb`. Confidence stays high because the rationale is written into the module doc comment and restated in `docs/action-support.md`, but the introducing PR discussion was not read.

**Best first step:** add the stable `code` to `AutomationError` and stop collapsing every failure into `-32000` in `Sources/SymOperateMCP/MCPServer.swift:34` — it is the smallest change that makes the agent-facing contract machine-readable, and the framing fix lands in the same file.
